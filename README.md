# School Management System

FastAPI + PostgreSQL backend, Next.js frontend. Built one phase at a time.

**Status: Phase 1 (Foundation) complete. Phase 2 (Settings, Students, Teachers, Parents): backend complete and tested; frontend pages are the next step.** Phases 3 to 6 are not started.

## Run it

### Docker (recommended)

```bash
cp .env.example .env
# set POSTGRES_PASSWORD and JWT_SECRET (openssl rand -hex 32) in .env
docker compose up --build
```

- App: http://localhost:3000  (APP_ENV=demo shows demo logins on the sign-in page)
- API docs: http://localhost:8000/docs

On Windows without Docker, run `run_services.bat` to apply migrations, seed the local
database, and start the backend and frontend; run `stop_services.bat` to stop those
processes. PostgreSQL must already be running. The first run creates
`backend/.env` from `backend/.env.example`; set `DATABASE_URL` and a random
`JWT_SECRET` there, then run the start script again. Install backend dependencies
from `backend/requirements-dev.txt` and frontend dependencies with `npm install`
in `frontend` before starting.

### Without Docker

```bash
# backend (Python 3.12, a running PostgreSQL 15+)
cd backend
pip install -r requirements-dev.txt
export DATABASE_URL=postgresql+asyncpg://sms:sms@localhost:5432/sms
export JWT_SECRET=$(openssl rand -hex 32)
alembic upgrade head
APP_ENV=demo python -m scripts.seed
APP_ENV=demo uvicorn app.main:app --port 8000

# frontend (Node 20+), in another terminal
cd frontend
npm install
npm run dev          # http://localhost:3000, proxies /api/v1/* to localhost:8000
```

Demo logins (APP_ENV=demo): `ceo`, `admin`, `teacher`, `student`, `parent`, all with `Demo@12345`.
Outside demo mode the seed creates only one admin from `FIRST_ADMIN_USERNAME` / `FIRST_ADMIN_PASSWORD`.

## Test it

```bash
# backend: needs an empty database called sms_test
export TEST_DATABASE_URL=postgresql+asyncpg://sms:sms@localhost:5432/sms_test
```

In Docker: `docker compose exec api pytest -q`.

## Decisions worth knowing about

- **Refresh tokens are opaque random strings, not JWTs.** Only a SHA-256 hash is stored, tokens rotate on every use, and replaying an old one revokes that whole login (a 10 second grace window absorbs two tabs refreshing at once). Access tokens are JWTs (15 min) held in memory only.
- **The browser only talks to the web origin.** Next.js rewrites `/api/v1/*` to FastAPI, so the httpOnly refresh cookie is first-party and CORS is not needed by the browser. `BACKEND_URL` is read at build time.
- **`sms_role` cookie is UX-only.** Middleware uses it to route people to the right area. It is not signed; real authorization is the signed access token plus the role in the database (a test proves a forged `role=admin` claim is ignored).
- **Usernames are stored lowercase** and matched case-insensitively at login. Phase 2 user creation must lowercase them.
- **Lockout:** 5 failed logins within 15 minutes locks the account for 15 minutes. A separate per-IP limiter (30 per 15 min) sits in front of login.
- **Small deviations from the schema in the spec:** `classes.sort_order` instead of a column named `order`; `fee_ledger` gained `paid_amount` and `fine_applied_at` (needed for partial payments and once-only fines); `users` gained `full_name`, `failed_login_count`, `first_failed_at`, `locked_until`; a `refresh_tokens` table was added; `school_settings` gained `fail_if_any_subject_failed` for the configurable pass rule.
- **Rate limiter is per-process.** Fine for one API container; it moves to Redis when the API is scaled out or for the public test endpoints in Phase 5.
- **Sidebar entries for later phases are visible** and lead to an "isn't available yet" page that names the phase. Say so if you would rather hide them until built.

## Phase 2 (backend)

Modules: **Settings** (school info + logo, academic years, classes, sections, subjects, class-subject marks, per-class monthly fee, user accounts), **Students**, **Teachers**, **Parents**. All under `/api/v1`; interactive docs at http://localhost:8000/docs.

| Area | Endpoints |
|---|---|
| Settings | `GET/PUT /settings`, `POST /settings/logo`, `GET/POST /academic-years`, `PUT /academic-years/{id}`, `POST /academic-years/{id}/set-current`, `/classes`, `/classes/{id}/sections`, `/sections/{id}`, `/subjects`, `GET/PUT /classes/{id}/subjects`, `GET/PUT /fee-structures` |
| Users | `GET /users`, `PUT /users/{id}/activate`, `PUT /users/{id}/deactivate`, `POST /users/{id}/reset-password` |
| Students | `GET/POST /students`, `GET/PUT/DELETE /students/{id}`, `POST /students/{id}/photo`, `PUT /students/{id}/status`, `PUT /students/{id}/discount`, `GET /students/{id}/ledger`, `GET /students/guardian-lookup?father_cnic=` |
| Teachers | `GET/POST /teachers`, `GET /teachers/me`, `GET/PUT/DELETE /teachers/{id}`, `POST /teachers/{id}/photo`, `PUT /teachers/{id}/assignments`, `PUT /teachers/{id}/salary-structure` |
| Parents | `GET /parent/children`, `GET /parent/children/{id}`, `GET /parent/children/{id}/dashboard` (read-only, no write routes) |
| Misc | `GET /meta/options` (values for the form dropdowns) |

Who can do what: Admin has full CRUD; CEO is read-only everywhere (including teacher salary data); Teacher sees students of assigned classes/sections and their own profile and salary; Student sees only themselves; Parent sees only linked children. An out-of-scope record returns **404**, never 403, so IDs can't be probed. The full role x endpoint matrix is tested (`tests/test_rbac_scoping.py`).

Key behaviours:

- **Student registration is one transaction**: roll number (`YYYY-NNNN`), guardian (reused when the father's CNIC already exists, so siblings share one guardian and one parent login), parent user, optional student login, 12 fee ledger rows, audit entry. Any failure rolls all of it back, including the roll number. Temporary passwords appear **only** in the registration response (`credentials`); the parent is `null` for a sibling.
- **Teacher registration** is one transaction too: employee ID (`EMP-NNNN`), login, salary structure, assignments (each `(class, subject)` must exist in the class's subject list). Gross salary is always computed by the server.
- **Fee ledger**: 12 monthly rows starting with the academic year's first month, due on `fee_due_day`, discount rounded half-up in `Decimal`. Changing a student's discount recalculates **unpaid rows only**.
- **Guardrails**: can't delete a class/section with students, or a subject in use (409 with an explanation); can't deactivate yourself or the last active admin; can't delete the only teacher of a class-subject without `force=true`; resetting a password ends all of that user's sessions.
- **Uploads**: JPEG/PNG/WebP only, 2 MB max, type detected from the file's bytes, stored under a random name in `UPLOAD_DIR`, served at `/api/v1/uploads/...` (a `StorageBackend` interface, so S3 can replace local disk).
- **Errors** now look like `{"detail": "...", "code": "VALIDATION_ERROR", "fields": {"guardian.father_cnic": "..."}, "request_id": "..."}`. List bodies are index-prefixed (`0.passing_marks`).

Seed (`python -m scripts.seed`, idempotent): in demo mode, creates Class 1 to 3 with sections A and B, 6 subjects (100/40), fees 2000/2500/3000, 3 teachers with assignments and salary structures, and 10 students through the same service the API uses, including one family with two children. It prints the demo logins. `demo` login `parent` sees both Khan children; `teacher` sees only the 6 students in Sadia Hussain's classes.

### Phase 1 files changed in Phase 2 (and why)

- `app/core/errors.py`: new error shape and upper-case codes, as the Phase 2 spec requires. Codes in Phase 1 tests were updated to match; `frontend/lib/api.ts` was updated to read the new shape (otherwise silent token refresh would have stopped working).
- `app/core/config.py`: upload settings, `SEED_SAMPLE_DATA`. `app/core/security.py`: `ahash_password` (Argon2 off the event loop); temp passwords are now 10 characters.
- `app/schemas/common.py`: default `page_size` is 10 (was 20). `app/utils/pagination.py`: optional `row_mapper` for joined queries.
- `app/services/counters.py`: `year` may be `None`. `app/services/audit.py`: `log_action()` helper.
- `app/models/enums.py`: student status `transferred` became `expelled`; added `Designation` and `Qualification`. `app/models/people.py`: `students.status_reason`; `guardians.father_cnic` is unique. Both via migration `0002`.
- `app/main.py`: mounts `/api/v1/uploads`. `app/api/v1/users.py`, `settings.py`, `router.py`: extended.
- `scripts/seed.py`: extended (demo `teacher`, `student`, `parent` logins now belong to real profiles; an old unlinked Phase 1 demo account of the same name is replaced).
- `pyproject.toml`: line-length rule relaxed for tests and the seed data tables. `docker-compose.yml`, `backend/Dockerfile`, `.env.example`: uploads volume and seed flag.

### Deviations from the Phase 2 spec

- `next_value` uses `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`, not `SELECT ... FOR UPDATE`. It takes the same row lock, and it also works for the very first number of a year, where there is no row yet to lock. Verified with 50 concurrent registrations.
- `GET /classes/{id}/subjects` and `GET/PUT /fee-structures` return a plain array (they are replaced as a whole). Every other list endpoint returns the paginated envelope.
- `POST /students` accepts an optional `discount_percent` (default 0) so the ledger discount math can be exercised at registration.
- `GET /students/guardian-lookup` and `GET /meta/options` were added; the registration form needs them ("Existing guardian found") and for dropdown values.
- Teacher date of birth is checked for age 18 to 70 (the spec only fixed the range for students).

### Known limitations and next-phase hooks

- Changing a student's class does not regenerate ledger rows (fees are Phase 4).
- Expelling or deactivating a student does not disable their login automatically; use Users > Deactivate.
- Uploaded files are served without authentication (unguessable random names). Add signed URLs when moving to S3.
- The duplicate-student check (same name, DOB and father CNIC) is not protected against two identical requests racing each other; the guardian and parent-account creation is.
- `latest_result`, `attendance_percentage`, `upcoming_tests` and `announcements` on the parent dashboard are always `null` (phases 3 to 6). Salary history and attendance tabs are placeholders for phase 4.
